go-union 每日模块讲解

`build_context/graph` DAG 上下文构建框架

这一套代码解决的不是“广告怎么选”，而是“在调用广告引擎之前，怎样把一个请求需要的上下文又快又稳地补齐”。 它把许多可并发的上下文计算拆成节点，用 DAG 统一调度，既能并发跑，又能在超时或失败时做降级恢复。

关键词：DAG 调度 关键词：BuildFlowContext 关键词：Fallback 降级 关键词：依赖触发

一句话作用

它像一个“并发装配车间”：先跑必须顺序执行的本地步骤，再并发跑异步节点；谁依赖谁，就等前置完成后再触发； 如果节点报错或超时，框架会尝试走 Fallback，尽量把请求补成“可继续”的状态。

它在业务里的位置

上游已经完成协议解析和代码位校验，下游马上要请求广告引擎。 这时 BuildFlowContext 会调用 DAG，把设备、地域、实验、广告位、搜索信息等上下文补齐。

1. 模块作用

为什么需要它

构建 FlowContext 的步骤很多，而且有些可以并发，有些必须等待前置结果。手写 goroutine 很容易失控，DAG 可以把依赖关系写清楚。

它负责什么

负责“调度”。也就是节点怎么组织、什么时候能开始、超时后怎么补救、结果何时回写到 FlowContext。

它不负责什么

它不直接决定业务规则。具体的“算什么字段”“查什么配置”是在节点自己的 Run 和 ParseResult 里完成。

3. 核心流程

把这套框架想成“先建施工图，再按依赖开工，最后把结果回填总对象”。

1. First Level LocalNode
先做顺序执行的初始化步骤
→
2. firstLevelMergeNode
把第一层收口
→
3. Async Node
并发查数据、算字段
4. ParseResult
在调度线程统一回写结果
→
5. Child Node Ready
依赖全部完成后继续触发
→
6. Final LocalNode
最后做收尾或汇总

构图阶段

  • NewBuilder 会先造一个虚拟 header 节点和一个 firstLevelMergeNode。
  • AddFirstLevelNode 加的是第一层本地节点，按加入顺序运行。
  • AddNode 加的是异步节点，可以声明依赖的父节点。
  • AddLocalNode 加的是同步节点，适合轻量计算或最后的整合动作。

运行阶段

  • Run 先执行第一层本地节点。
  • 当某个节点完成后，tryPrepareChildNodes 会把所有孩子节点的依赖计数减一。
  • 某个孩子的 parentNodeLeftCount 变成 0，说明它的依赖已满足，可以开始。
  • 异步节点完成后，不会自己写入 FlowContext，而是交给调度线程调用 ParseResult。
最关键的设计点：异步节点的 Run 不能直接改 FlowContext。框架故意把“并发执行”和“结果回填”拆开，避免多个 goroutine 同时写共享对象，降低可见性和竞态问题。

4. 重要结构体与函数

名字 看法 要点
Node 异步工作单元 有 Run、Fallback、ParseResult、IsRecoverable。适合耗时操作，比如查配置、查画像、远程取数。
LocalNode 同步工作单元 直接在调度线程执行，可以写 FlowContext，适合初始化、轻量加工、最后汇总。
DAGBuilderImpl 施工图设计师 负责把“节点”和“依赖关系”组装成内部图结构。
RunnableNode 运行时节点快照 除了原始节点信息，还记录开始时间、结束时间、剩余依赖数、状态等。
RunningPlan 一次请求的调度现场 里面有 ready 队列、结果通道、剩余节点数、最后错误、是否超时。
runNode 统一入口 本地节点走同步执行；异步节点走 goroutine；超时恢复模式下则直接走 Fallback。
parseAsyncNodeResult 异步收口点 如果 Run 返回错误且节点可恢复，会先试 Fallback，然后再 ParseResult。
tryRecoveryTimeoutDag 超时补救逻辑 对未完成的异步节点尝试降级；如果还能继续，就继续触发后续节点；不行则整体失败。

5. 一个具体例子

用 dag_test.go 里的超时恢复思路来理解，最直观。

场景

第一层先跑 fist_1、fist_2。然后一个本地节点 adLocal_1_1 完成后，触发多个异步节点： async_1_1、async_1_2、async_1_3。其中有节点会故意睡很久，制造超时。

结果

如果这些慢节点是可恢复的，框架会在超时后走 Fallback，把必须的默认值补上，然后继续触发依赖它们的后续节点。 所以最终返回可能是 timeout = true 但 err = nil。 

BuildFlowContext
  -> first local init
  -> async node A 正常返回
  -> async node B 超时
  -> DAG 进入 recovery 模式
  -> 对 B 调用 Fallback
  -> ParseResult 把降级结果写回 FlowContext
  -> 依赖 B 的后续节点继续执行
  -> 请求继续往 engine 走

这就是它的业务价值：不是所有超时都等于“整条链路必须失败”。有些上下文字段允许降级，系统就还能继续给广告引擎一个“够用的上下文”。

6. 容易混淆的点

混淆点 1：Run 和 ParseResult

很多人第一次看会问：既然 Run 都算完了，为什么还要 ParseResult？ 答案是为了把“并发执行”与“共享对象写入”分开，统一在调度线程回写，减少并发写风险。

混淆点 2：为什么还有 LocalNode

不是所有节点都值得起 goroutine。很轻的步骤、顺序敏感步骤、最后整合步骤，直接本地跑更简单、更省调度成本。

混淆点 3：timeout=true 但不一定失败

这是这套设计最反直觉的一点。超时表示“真实运行里发生过超时”，但如果所有必要节点都能恢复成功，整体仍可继续。

混淆点 4：merge node 不是业务节点

它只是结构辅助点，用来简化“后续节点默认依赖前面一批节点”的表达。它本身不做业务逻辑。

7. 学习小结

如果把 build_context 看成“给广告请求补齐档案”，那 graph 就是这套档案装配流水线的调度器。 它最值得学习的地方有三点：

  • 用 DAG 显式表达依赖，而不是把顺序和并发写死在代码流程里。
  • 把异步执行和结果回填拆开，降低并发写共享对象的复杂度。
  • 把超时视为“可恢复的中间状态”而不是“绝对失败”，让广告请求在有限降级下继续向前走。

下一次如果继续深挖，最自然的延伸是：去看真实的 DAG 节点到底在补哪些上下文字段，以及 ADN 和 DSP 两条图在节点组成上有什么差异。
