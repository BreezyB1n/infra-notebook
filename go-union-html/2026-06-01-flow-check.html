go-union 每日模块拆解

Flow Check：广告请求进入主流程前的“安检口”

如果把 v2/adfetch 想成一条广告请求装配线，那么 flow_check 就是正式开工前的安检口。 它不负责召回广告，也不负责拼结果；它专门回答一个更基础的问题： 这个请求到底有没有资格继续往下走？

今天这页重点看 v2/adfetch/flow_check。它位于 protocol_mapping 之后、 build_flow_context 之前，负责把“原始请求”升级成“带配置、带规则上下文的请求”，并在必要时尽早拦截。

一句话理解

protocol_mapping 负责“把请求翻译成系统能读懂的格式”，而 flow_check 负责“确认这个格式化后的请求是否合法、可投、值得继续”。

早失败 统一拦截口 按接入方式分流 补齐 app / rit 配置

你会学到什么

  • 为什么系统要在主流程前做一次集中校验
  • SDK 请求和 DSP 请求为什么不能共用同一套 checker
  • BidRequestWithRitInfo 为什么是后续链路的关键中间形态
  • 真实请求是怎么在这里被放行、修正或拦截的

1. 模块作用

作用 1：做前置安检

先检查 app_id、rit、广告位大小、包名、广告数量、SDK 版本、签名、动态布局等基础条件，避免坏请求继续污染后面流程。

作用 2：补齐配置上下文

它会先通过配置服务查出 ritConfig 和 appConfig，再组装成 BidRequestWithRitInfo，让后续模块不必反复查配置。

作用 3：按入口选规则

SDK、DSP、M2S 社群、开放注册等流量规则不一样，所以这里会分出不同 checker 列表，而不是把所有规则揉成一锅。

最值得记住的一点： flow_check 不是简单的 if ... else 大杂烩，它更像“统一校验框架 + 多组可组合 checker”。 这就是它适合教学的地方。

2. 关键文件

文件 角色 看点
v2/adfetch/ad_fetch.go 真实调用入口 主链路里先做 protocol_mapping，再做 flow_check，之后才会进入 light_drop 和 build_flow_context。
v2/adfetch/flow_check/flow_check.go 框架骨架 定义 SDK / DSP 两类 FlowCheck 构造方式，串起“补配置 + 逐个 checker 执行 + 错误打点”。
v2/adfetch/flow_check/checker_interface.go 统一接口 AtomicChecker 和 FunctionalChecker 把校验逻辑抽成统一积木。
v2/adfetch/flow_check/base_check.go 通用规则 校验 sourceType、server bidding、一些 app / slot / 包名 / ad_count 基础条件。
v2/adfetch/flow_check/sdk_check.go SDK 专属规则 低版本拦截、动态布局、签名校验、开放注册、预览合法性等都在这里。
v2/adfetch/flow_check/dsp_check.go DSP 专属规则 只关心 DSP 世界里的 adx、平台、广告位数量和尺寸等约束。
v2/adfetch/flow_check/media_config.go 配置读取层 从 shm / site config 取出 ritConfig 和 appConfig，是“请求绑定配置”的入口。
v2/adfetch/entity/bid_request_with_rit_info.go 中间形态 把原请求包一层，挂上 rit / app 配置，并顺手做一些初始化与重写。
v2/adfetch/flow_check/sdk_check_test.go 案例支撑 比如动态布局校验的测试，能帮助理解规则不是拍脑袋写的。

3. 核心流程

先看主链路中的位置，再看包内部怎么做。

步骤 1 protocol_mapping

把 HTTP / PB / 路由差异翻译成统一请求对象。

→
步骤 2 flow_check

查配置、补 rit / app 上下文、跑一串 checker。

→
步骤 3 light_drop

在更完整的请求基础上做轻量降级。

→
步骤 4 build_flow_context

真正为召回 / 排序 / 打包准备大上下文。

包内主流程

  1. 检查明显错误，比如 app_id、rit 是否为空。
  2. 用 ModisConfigService 查出 ritConfig 和 appConfig。
  3. 调用 entity.NewBidRequestWithRitInfo(...) 生成增强版请求。
  4. 遍历 checkerList，逐个执行 checker.Check()。
  5. 一旦某个 checker 返回 error，就停止继续执行，并打错误 metrics。

为什么这一步很省钱

因为很多请求如果到了 engine、pack、send 才发现不合法，前面已经浪费了一大堆计算和依赖调用。把错误尽量提前挡住，本质上是在保护后面的高成本模块。

ad_fetch.go 主链路（抽象理解）
protocol_mapping
  -> flow_check
    -> 用 rit/app 配置构造 BidRequestWithRitInfo
    -> 依次跑 base checker / sdk checker / dsp checker
    -> 有错就提前返回
  -> light_drop
  -> build_flow_context
  -> engine
  -> pack
  -> send

4. 重要结构体 / 函数

FlowCheck

SDK 主校验器。内部持有 checkerList 和 appConfigService。它的价值不在“自己做了多少规则”，而在“把校验流程标准化”。

DspFlowCheck

DSP 的独立版本。你可以把它理解成“同一个框架骨架，但换了一套更适合 DSP 场景的 checker 集”。

AtomicChecker

最核心的抽象。每个 checker 都只关心一件事：给定一个增强后的请求，我要不要拦它？

NewFunctionalChecker

把一个函数包装成 checker，降低新增规则的门槛。很多规则就是靠这个工厂函数快速拼起来的。

NewBaseChecker()

返回一组通用 checker，比如 sourceType、server bidding、app 状态、广告位信息、包名和 ad_count 校验。

NewSdkCheckerList()

返回 SDK 专属规则清单，包括低版本拦截、动态布局、签名、开放注册、预览合法性等，更贴近客户端接入现实。

函数 / 结构 你该怎么记 典型职责
entity.NewBidRequestWithRitInfo “原始请求升级器” 把请求和 app / rit 配置绑在一起，并初始化一些后续链路会依赖的字段。
ModisConfigService.GetRitConfig “查广告位配置” 从 shm 取到 rit 对应的站点位配置。
ModisConfigService.GetAppConfig “查媒体配置” 从 relation site / media / site config 拼出 app 侧配置对象。
NewPackageNameChecker “请求包名和平台包名对不对得上” 支持单包、模糊匹配、多包、白名单豁免等分支。
NewDynamicChecker “动态布局别乱来” 会结合 SDK 版本、render_method、国际化环境、代码位样式等多条件判断是否放行。
M2SCommunitySignCheck “社群请求先验签” 检查 sign、nonce、timestamp，并按约定算法重算签名。

5. 一个具体例子

下面拿一个最典型、也最容易代入的例子：SDK 的 get_ads 请求进入 flow_check 后，到底经历了什么？

输入状态

  • protocol_mapping 已经把原始请求转成 BidRequestWithProtocolHeader
  • 请求里有 app_id、rit、adslots、ad_sdk_version
  • 这时它还没有绑定平台配置，也还没跑各种合法性规则

flow_check 内部动作

  • 先确认 app_id 和 rit 不是空的
  • 读取 ritConfig 和 appConfig
  • 组装成 BidRequestWithRitInfo
  • 先跑 base checker，再跑 sdk checker
  • 如果有任何一条命中拦截，就立刻返回 error

例子：动态布局请求被拦截

假设某个请求命中了动态布局代码位，但客户端 SDK 版本过低，或者 render_method 和代码位实际样式不匹配。 这时 NewDynamicChecker 会结合样式配置、版本号、请求类型和环境做判断，返回 UnionDynamicPlanBlock 之类的错误。

从业务角度看，这相当于在说： “不是没有广告，而是你这次请求的展示能力和代码位要求对不上。” 

你可以把这个例子脑补成：

客户端请求来了
  -> 代码位是动态布局
  -> 但 SDK 版本太低 / render_method 填错
  -> flow_check 提前挡住
  -> 后面的 engine / pack 根本不需要再浪费时间
测试侧证据： sdk_check_test.go 里就有围绕 NewDynamicChecker 的测试， 例如“直播内流 render method 校验跳过”这类场景，说明这些规则已经被当成独立行为在验证，而不是散落在大流程里碰运气。

6. 容易混淆的点

混淆点 1：flow_check 不是 protocol_mapping

protocol_mapping 解决“怎么读懂请求”，flow_check 解决“读懂之后让不让过”。前者偏协议翻译，后者偏业务合法性。

混淆点 2：它不只是校验，还会补上下文

很多人以为这里只是 return error。其实它还做了关键的配置绑定，把请求升级成 BidRequestWithRitInfo，后面很多模块都吃这个对象。

混淆点 3：SDK 和 DSP 不是同一套规则

DSP 只看 DSP 世界里的约束；SDK 还要面对客户端版本、包名、签名、开放注册等问题。两边虽然都叫 flow_check，但关注点不一样。

混淆点 4：checker 返回 nil 不代表“什么都没发生”

有些 checker 会顺手打 metrics、修正 app_id、改请求字段，甚至触发一些初始化逻辑。它不报错，不等于它没有副作用。

再补一个很常见的误区： 看到 NewSdkFunctionalChecker 这个名字，容易以为“它只是命名不同”。 其实它是真的在包装层判断 accessMethod，避免非 SDK 请求误跑 SDK 规则。

7. 学习小结

从工程角度看

flow_check 的价值，是把“前置校验”做成一个独立、可组合、可扩展的模块，而不是把校验散落到主流程各处。

从业务角度看

它在尽量早的阶段挡掉无效请求，既保护后面的高成本链路，也让错误码和拦截原因更容易被统一观测。

今天你至少要带走 3 句话

  • flow_check 是 v2/adfetch 主链路里的“前置安检口”。
  • 它的核心产物不是只有 error，还有 BidRequestWithRitInfo 这个增强后的请求对象。
  • 它最漂亮的设计点，是把规则拆成一组组 checker，让 SDK / DSP / 特殊场景能各走各的校验路线。
如果你明天继续学： 最自然的下一站是 v2/adfetch/protocol_mapping/sdk 或 v2/adfetch/context_drop。 前者能接上“请求是怎么被翻译出来的”，后者能接上“为什么过了 flow_check 以后还会被进一步降级 / 拦截”。
