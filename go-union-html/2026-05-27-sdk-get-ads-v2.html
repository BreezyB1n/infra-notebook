SDK get_ads v2 主链路

这是第一次读 go-union 时最值得抓住的一条线。因为它同时覆盖了 “路由入口怎么进来、服务怎么组装、请求怎么变成内部对象、上下文怎么补齐、engine 和 pack 怎么串起来、最后怎么返回客户端”。 如果这条链路读顺了，后面再看 DSP、内容联盟、server bidding，会轻松很多。

学习主题
入口到响应的完整 get_ads 链路
推荐读者
第一次接触 go-union 的同学
核心关键词
ProtocolMapping / FlowContext / Engine / Pack

1. 模块作用

可以把这条链路想成一个“广告请求装配流水线”。

客户端调用 /api/ad/union/sdk/get_ads/ 后，系统并不是直接去拿广告，而是先把外部请求整理成内部统一格式，再补全上下文，再调用广告引擎，再把候选广告打包成客户端真正能展示的素材。

它解决什么问题？

外部 SDK 请求格式不稳定、字段很多、逻辑分支复杂，不能直接拿去调用 engine。v2 链路把“杂乱输入”整理成“稳定内部流程”。

为什么它适合入门？

因为它是很多场景复用的母体。你读懂它，就能理解 go-union 不只是一个 HTTP handler，而是一套阶段化广告处理框架。

2. 关键文件

文件 职责 读这个文件时要看什么
main.go 注册路由，决定请求从哪个 handler 进入 确认 /api/ad/union/sdk/get_ads/ 绑定到 view.GetAdsV2Sdk
view/v2_get_ads.go 初始化 v2 服务，把各阶段组件组装成 GetAdsService 看 builder 注入了哪些组件，以及 SDK 场景和其他场景的差异
v2/adfetch/ad_fetch.go 主流程骨架 重点看 GetUnionAds 里的 step 链

3. 核心流程

主流程虽然很长，但第一次学习时可以先切成 4 段。

A. 入口分发
路由把请求送到哪？
main.go 把 /api/ad/union/sdk/get_ads/ 注册到 view.GetAdsV2Sdk。 这个 handler 先做单机流控，再调用 v2GetAdsService.GetUnionAds。
Route → GetAdsV2Sdk → limiter.Allow() → v2GetAdsService.GetUnionAds
B. 请求整理
外部请求先变成内部统一请求。
SDK 协议映射会读 body、解密、格式化、转成 protobuf，再构造 BidRequestWithProtocolHeader。这一步还会生成服务端 request id， 并把 header、path、客户端 IP、access method 等信息一起塞进去。
protocol_mapping → sample_log → flow_check → light_drop
C. 生产广告
先补齐上下文，再去 engine 拿候选。
build_flow_context 会用 DAG 生成 FlowContext； 然后 ad_engine 去拿候选广告；随后 pack 把候选广告变成可以展示的素材。
build_flow_context → context_drop → ad_engine → handle_async_pack → pack
D. 返回与副作用
返回给客户端只是表面，后面还有日志、ack、指标。
write_out 把打包结果映射成 SDK 响应； async 里还有异步日志、ack、样本、超时指标等收尾动作。
search_lu_debug_and_cut → write_out → async

4. 重要结构体 / 函数

GetAdsService

它不是“一个函数”，而是一组阶段组件的容器。里面挂着 ProtocolMapping、FlowCheck、FlowContextBuilder、 Engine、Packer、Sender、Acker 等接口。 所以它本质上是“广告链路编排器”。

GetAdsServiceBuilder

它负责组装阶段组件。SDK 场景走 NewDefaultSdkFlowChecker 和 NewSdkLightWeightDrop，说明不同流量场景能复用骨架，但替换局部实现。

BidRequestWithProtocolHeader

它是“整理后的标准请求”。除了原始 BidRequest，还带着 header、URL、客户端 IP、 access method、request type、server request id 等运行时信息。

FlowContext

这是整条链路的核心上下文。你可以把它理解成“请求在系统内部活着时的总状态对象”。 从设备、用户、点位、实验、地理、engine、pack，到 ack 需要的信息，都会逐步塞进来。

SdkProtocolMapping.MappingToBidRequest

这是外部世界进入内部世界的门。它做的不是简单反序列化，而是“解密 + 清洗 + 规范化 + 构造标准对象”。

AdnContextGraph.BuildFlowContext

这里的重点是 DAG。说明上下文补齐不是一条简单顺序函数，而是一个可以管理依赖关系的图。 这也是 v2 链路工程化程度比较高的地方。

5. 一个具体例子

假设客户端发来一个普通 SDK 拉广告请求：
  1. 请求打到 /api/ad/union/sdk/get_ads/。
  2. GetAdsV2Sdk 先过限流，没超就进入 GetUnionAds。
  3. protocol_mapping 把加密 body 解开，转成 pbgen.BidRequest，再包装成 BidRequestWithProtocolHeader。
  4. flow_check 检查 app、rit、请求合法性；light_drop 做轻量过滤。
  5. build_flow_context 通过 DAG 把设备、实验、位置、投放上下文补齐，形成 FlowContext。
  6. ad_engine 去广告引擎取候选广告，得到 FlowContextWithAdsList。
  7. pack 把候选广告转成素材，得到 FlowContextWithAdMaterial，里面的 AdMaterialist 就是最终可返回的广告素材列表。
  8. write_out 把素材抽成 SDK 响应 JSON / protobuf 结构，客户端拿到 creatives。
  9. async 再补做 ack、日志、指标等异步工作。

这个例子最关键的收获不是“有哪些函数”，而是明白对象在不断升级： 原始 body → BidRequest → BidRequestWithProtocolHeader → BidRequestWithRitInfo → FlowContext → FlowContextWithAdsList → FlowContextWithAdMaterial。

6. 容易混淆的点

混淆点 1：GetAdsV2Sdk 不是主逻辑，它只是入口。 真正的大部分业务逻辑都在 GetAdsService.GetUnionAds 里。入口层负责接住请求、做一点前置控制，然后把请求交给服务骨架。
混淆点 2：ProtocolMapping 不只是“解析 JSON”。 它还负责解密、字段格式化、服务端 request id 生成、环境信息拼装，所以它更像“协议适配器”，不是普通反序列化器。
混淆点 3：FlowContext 和 BidRequest 不是一回事。 BidRequest 更像客户端原始请求； FlowContext 则是内部处理态，里面已经塞进了大量派生信息和中间结果。
混淆点 4：pack 不是“可有可无的美化步骤”。 engine 给的是候选广告信息，客户端最终需要的是可展示素材。pack 是把“候选广告”变成“能展示 Creative”的关键步骤。
混淆点 5：链路返回成功，不代表工作已经结束。 write_out 后面还有 async。很多样本、ack、日志、统计指标都在这里补齐，所以读链路时不要只盯着“返回响应”。

7. 学习小结

第一次学习 go-union，最应该建立的认知是： 它不是一个“写死在 handler 里的广告接口”，而是一套可组装、可替换阶段组件的广告请求流水线框架。

今天至少要带走的 3 个结论

1. view 层负责分诊和组装，不是全部业务本体。
2. GetAdsService 是骨架，真正靠接口组件拼出不同场景。
3. 主链路的对象是在逐步升级的，不是一开始就拿到最终广告。
