dynamic_slot_ab：一次“动态广告位分流”查询是怎么设计出来的？

这个模块的职责不是直接返回广告，而是回答另一个更前置的问题：当前这个用户、这个 code group，最终应该命中哪个 rit，以及它对应什么广告位类型。你可以把它理解成“投放前的分流咨询台”。

它很适合学习 go-union 的组件化写法，因为这里把请求解析、AB 选择、结果包装、事件日志拆成了几个清楚的小角色。虽然主入口当前还没接完整逻辑，但模块轮廓已经非常标准。

一句话先理解

输入：一个加密的动态分流请求，里面带 code_group_id、设备信息、App 信息。

中间要做的事：解密请求、找出用户身份、根据 code group 和 AB 信息挑 rit、查出广告位类型、记录日志。

输出：一个加密响应，告诉调用方这次应该用哪个 rit 和什么 ad_slot_type。

今天重点学什么

Builder 组装服务 Protocol Mapper AB 容错兜底 埋点字段设计

1. 模块作用

动态广告位场景里，一个 code_group_id 往往不是单个固定广告位，而是一组候选 rit。服务要结合用户身份和 AB 分流结果，从这组候选里选出一个“本次该走的 rit”。

它解决的不是“广告内容选什么”，而是“广告位先落到哪条支路上”。这是更靠前的一次路由决策。

2. 关键文件

文件 角色 你读它时要关注什么
view/dynamic_slot_ab.go 入口层 看 service 是怎么被初始化的。它把 mapper、getter、logger 像积木一样拼起来。
v2/dynamic_slot_ab/dynamic_slot_ab.go 服务骨架 重点看 DynamicSlotAbServiceBuilder。真正的主流程还没补完，但依赖边界已经划清。
.../protocol_mapping/dynamic_protocol_mapping.go 协议映射层 输入请求怎么读 body、解密、校验、转成内部结构；输出结果怎么重新加密。
.../ab_info_get/ab_info_get.go AB 分流决策层 怎么调用 tester.GetAbRitInfo，以及失败时怎样回退到默认 rit。
.../event_log/event_log.go 日志层 看它把请求、上下文、结果、错误一次性打成完整事件，便于排查线上问题。
.../entity/*.go 领域对象 看请求、上下文、结果是怎样一层层“包起来”的。

3. 核心流程

入口初始化 service

createDynamicSlotAbService 用 Builder 注入三个核心组件：protocolMapper、abInfoGetter、eventLogger。

把外部协议转成内部请求

MappingToDynamicRequest 读取 HTTP body，解密 message，再反序列化成 DynamicRequest。

补齐动态上下文

虽然当前文件里还没把这段流程真正写进 GetDynamicSlotInfo，但从 DynamicContext 结构能看出设计意图：把用户信息、全局 did、code group 信息都补进去。

根据 AB 信息挑 rit

GetDynamicAbRitInfo 调 tester.GetAbRitInfo。如果拿到非法 rit、空 rit、或者 rit 不在候选 CodeIds 里，就回落到 DefaultCodeId。

查询广告位类型

代码会用最终 rit 去查 shm.GetSiteCodeInfoById，再把站点配置转成 AdSlotType。这一步让“rit 选择结果”变成“客户端可消费的广告位信息”。

返回加密响应并记录事件

MappingOutResult 生成 {rit, ad_slot_type, dynamic_slot_ab_extra}，优先加密返回；DynamicEvent 则把全过程打到 message bus。

4. 重要结构体 / 函数

DynamicRequest

外部请求的核心载体。至少要有 code_group_id、device.os、device.applog_did、app.appid。

这里的 binding:"required" 很关键，说明协议层在第一步就会拦掉缺字段请求。

DynamicContext

是“解析后的请求”再加上“用户维度信息”和“code group 配置”的合体对象。

你可以把它理解成：请求原文 + 路由所需上下文。

GetDynamicAbRitInfo

模块里最像“业务决策”的函数。它不相信外部结果，始终会做两层兜底：

  • 取不到 AB rit，就回默认 rit。
  • 取到了，但不合法或不在候选集合里，还是回默认 rit。

MappingOutResult

把内部结果转回客户端协议。这里能看到 go-union 的一个常见习惯：优先返回加密消息，失败时再退化到明文，保证服务尽量可用。

5. 一个具体例子

测试代码里有一组很适合拿来理解的例子：

请求里的 code group 1234
候选 CodeIds [22345, 22356, 22367]
默认 DefaultCodeId 22345
tester 返回 rit 如果返回 "aabbcc" 或 "22349" 这种非法值 / 越界值，服务都会丢弃。
最终 rit 回退成默认值 22345
最终 ad_slot_type 根据站点配置映射成如 BANNER 这样的广告位类型。
这段逻辑很像“老师分班”：先看推荐分班结果，如果推荐结果无效，还是回原始默认班级，不能把学生分到一个不存在的班里。

6. 容易混淆的点

混淆点 1：它是不是广告召回接口？

不是。它不负责选广告素材，也不跑完整 engine/pack。它主要负责动态广告位分流，产出的是 rit 和广告位类型。

混淆点 2：AB 结果是不是直接信任？

也不是。GetDynamicAbRitInfo 会再次验证 rit 是否是数字、是否在候选集合、是否能查到站点配置。它对坏数据是保守的。

混淆点 3：入口为什么现在只返回 not support？

因为主流程还没在 GetDynamicSlotInfo 里接起来。今天更适合把它当成“骨架阅读题”：看清它想怎么组织依赖、怎么分层，而不是把它误看成完整成品。

混淆点 4：为什么日志这么重？

这种分流接口出了问题，排查时最怕“只知道失败，不知道失败前用户命中了什么上下文”。所以日志把请求、解密内容、用户信息、最终 rit、错误码都带上了。

阅读这类模块时，不要只盯入口函数是否“能跑通”。很多时候最有学习价值的，是它已经露出来的分层边界和容错思路。

7. 学习小结

dynamic_slot_ab 是一个很典型的 go-union 小型服务骨架：

  • 入口层只负责接线，不写重业务。
  • 协议层负责“外部格式 ↔ 内部对象”的转换。
  • 业务层负责做 rit 选择和容错。
  • 日志层保证线上问题可回放、可追踪。

如果你是第一次读 go-union，今天最值得带走的不是某个字段名，而是这套思路：先把职责拆薄，再用 Builder 把它们拼起来。后面读 adfetch、pack、dsp_v2_get_ads 时，你会反复看到这个模式。

讲解依据：`view/dynamic_slot_ab.go`、`v2/dynamic_slot_ab/*.go` 及其测试文件。特别注意：当前主入口尚未实现完整业务逻辑，本文重点是帮助理解模块设计和预期链路。
